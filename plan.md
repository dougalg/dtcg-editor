# Implementation Plan: Edit Dimension Tokens in Browser

## Overview
This feature closes three gaps flagged as deliberate, temporary in earlier features: `token-core` gets its first `serialize()` path, the Token-Type Package Contract goes from documented-but-unimplemented to a real interface with its first concrete implementation (`dimension`), and the web app gains its first write path alongside the existing read-only one. The design keeps the existing plugin boundary intact: `token-core` stays completely agnostic of what "dimension" means — it only knows how to locate a token by path, patch its name/value/description, and re-serialize a tree. All type-specific knowledge (the Dimension `$value` shape, its edit UI) lives in the new `@dtcg-editor/token-type-dimension` package, which implements a new `@dtcg-editor/token-type-contract` interface. The web app is the only layer that knows "dimension is the one editable type today" — extending that set later is an `apps/web-app` change, not a `token-core` change.

Per the DTCG spec (designtokens.org/tr/2025.10/format), a Dimension token's `$value` is `{ "value": <number>, "unit": "px" | "rem" }` — no other units are valid, and `unit` is required even when `value` is `0`.

## Architecture Decisions
- **Round-Trip Fidelity is satisfied by rebuilding the tree, not by preserving source formatting.** `docs/project.md`'s constraint explicitly allows formatting/key-ordering to normalize as long as the *data* round-trips — so `serializeTokenFile` rebuilds a plain JS object from the `TokenDocument` tree and `JSON.stringify`s it, rather than doing source-preserving/AST-based editing (which would need a new dependency, unjustifiable here). Untouched tokens' `value: unknown` already carries the exact structure `JSON.parse` produced, so they serialize back unchanged with zero extra work; only tokens with pending edits get their `value`/`name`/`description` replaced.
- **`token-core` stays type-agnostic; the edit validity check ("is this token's effective type currently editable") lives in `apps/web-app`.** `applyTokenEdits` (new, in `token-core`) accepts an already-validated raw `value: unknown` and just does generic tree surgery (locate node, rename with sibling-collision checking, patch fields) — it has no concept of "dimension." The route handler is what checks `resolveEffectiveType(...) === "dimension"` before calling it. This matches the existing Token-Type Package Contract principle that the core engine never hard-codes a specific type.
- **`apps/web-app` moves to Vitest; `token-core`, `token-type-contract`, and `token-type-dimension` stay on `node:test`.** Verified empirically before deciding: `node --test` on a trivial `.tsx` file fails with `ERR_UNKNOWN_FILE_EXTENSION` — Node doesn't even recognize the extension, let alone transform JSX (its native TypeScript support only *strips* type syntax; JSX requires an actual code transform, which is out of scope for that feature entirely). This is the "concrete gap" `docs/project.md`'s Testing convention already anticipates as the bar for adding a third-party test framework. Scope: only `apps/web-app` renders/tests components, so only it changes runners — `token-core`/`token-type-contract`/`token-type-dimension` have no JSX in their test files and stay on `node:test` unchanged. Within `apps/web-app`, *all* existing `node:test` files migrate to Vitest too (import swap only: `test`/`before`/`after` from `"vitest"` instead of `"node:test"`, hooks renamed to `beforeAll`/`afterAll`; existing `node:assert/strict` assertions are left exactly as-is, since Vitest doesn't require its own `expect` and importing `assert` still works) — this keeps exactly one test runner per package rather than two selected by file extension. New devDependencies (`apps/web-app` only): `vitest`, `@vitejs/plugin-react` (Vitest's standard React-JSX transform, needed since the default esbuild transform alone doesn't reliably match the automatic JSX runtime Next.js/React 19 expect), `jsdom` (the DOM environment Vitest renders components into — no built-in Node alternative exists), `@testing-library/react` (queries rendered output the way a user would, the standard pairing for component tests, avoiding a hand-rolled DOM-assertion harness). Deliberately *not* adding `@testing-library/jest-dom` or `@testing-library/user-event` — plain DOM property assertions (`element.textContent`, `element !== null`) and `fireEvent` cover this feature's needs without the extra dependencies.
- **`@dtcg-editor/token-type-dimension`'s `DimensionEditor` component gets no Vitest config of its own.** It's exercised indirectly through `apps/web-app`'s `EditableTokenTree` component test (which renders it as a child) rather than adding a second package's worth of Vitest/testing-library setup for one controlled-input component — kept in mind as a scoping call, not an oversight, if a future token-type package's editor needs isolated testing.
- **`docs/project.md`'s Testing line (Tech Stack section) needs updating at `/sdd-archive`** to reflect the per-package split (`token-core`/`token-type-*`: `node:test`; `web-app`: Vitest) — noted here so it isn't missed, following this repo's established pattern of deferring `project.md` updates to the archive step.
- **Client-side edit application is optimistic and local, not a full-page refresh.** After a successful save, the client applies the same edits to its own in-memory copy of the tree and clears pending state — it does not call `router.refresh()`. This avoids a timing race between clearing "pending" state and a Server Component re-fetch landing, at the cost of maintaining two small, parallel "apply an edit to a tree" implementations: `token-core`'s `applyTokenEdits` (server-side, `Map`-based `TokenDocument`) and a new `applyEditsToPlainNode` (client-side, array-based `PlainDtcgNode`). This mirrors the existing `DtcgNode`/`PlainDtcgNode` split already in the codebase (`lib/tokens/plain-node.ts`), so it's consistent with, not a departure from, current practice.
- **`PATCH /api/tokens/[...path]`**, same route file as the existing `GET`, following the established "thin exported handler wraps an injectable function" pattern from the Result-pattern migration feature.
- **New packages depend on React as a regular `dependency`, not a `peerDependency`.** No package in this repo uses `peerDependencies` yet; introducing the convention for just these two packages would be inconsistent without a stated reason. Worth revisiting if/when packages are published for external consumption.

## Implementation Steps

### Step 1: `token-core` — generic tree editing and serialization
- [x] Add `TokenSerializeError` and `serializeTokenFile(document: TokenDocument): Result<string, TokenSerializeError>` in a new `src/serialize.ts` — walks the tree, rebuilds a plain object per node (group: metadata + `$`-prefixed extensions + children; token: `$value`/`$type`/`$description`/`$deprecated` + extensions), wraps the final `JSON.stringify` with `fromThrowable`.
- [x] Add `findNode(root: GroupNode, path: readonly string[]): { node: DtcgNode; ancestors: GroupNode[] } | undefined` in `src/resolve-type.ts` (alongside `resolveEffectiveType`, since it's the same kind of generic tree lookup).
- [x] Add `TokenEditError` and `applyTokenEdits(document: TokenDocument, edits: readonly TokenEdit[]): Result<TokenDocument, TokenEditError>` in a new `src/edit.ts`. `TokenEdit = { path: readonly string[]; name?: string; value?: unknown; description?: string }`. For each edit: locate the node (error if missing or not a `"token"`), check sibling-name collision if `name` is provided and differs from the current name (error if taken), then produce a new, immutably-rebuilt tree with the patched token (and its new key in the parent's `children` Map, if renamed).
- [x] Export `serializeTokenFile`, `TokenSerializeError`, `findNode`, `applyTokenEdits`, `TokenEditError`, `TokenEdit` from `src/index.ts`.
- Files: `packages/token-core/src/serialize.ts`, `packages/token-core/src/edit.ts`, `packages/token-core/src/resolve-type.ts`, `packages/token-core/src/index.ts`

### Step 2: `@dtcg-editor/token-type-contract` (new package)

### Step 4: `apps/web-app` — write path (server)
- [x] `lib/tokens/write.ts`: `writeAndSerializeTokenFile(rootDir, relativePath, document, logger)` — resolves the safe path via the existing `resolveSafeTokenPath`, calls `token-core`'s `serializeTokenFile` internally (mirroring `readAndParseTokenFile`'s "read, then parse" combo symmetrically as "serialize, then write" — takes a `TokenDocument`, not a pre-serialized string, slightly refining the plan's original signature), then `ResultAsync.fromPromise(writeFile(...), ...)` classified as a logged `UnknownError` on failure.
- [x] Request-body schema (Zod, validated at this new edge) in new `lib/tokens/edit-request.ts`: `EditRequestSchema`.
- [x] Added an injectable `patchTokenFile(request, relativePath, logger)` to the existing `app/api/tokens/[...path]/route.ts`, wrapped by a thin exported `PATCH`, following the established pattern from `app/api/tokens/route.ts`'s `listTokenFiles`. Flow implemented as planned: parse body (400 on malformed) → `EditRequestSchema` validation (400) → `readAndParseTokenFile` (400/404/422/500 mapped as `GET` already does) → for each edit, `findNode` + `resolveEffectiveType` (400 if not `"dimension"`) → `dimensionTokenType.valueSchema.safeParse` if `value` present (400 on invalid shape) → sibling-collision pre-check if `name` present (400 on collision) → `applyTokenEdits` with all validated edits (400 on any structural edit error) → `writeAndSerializeTokenFile` (500 on write failure) → `200 { ok: true }`.
- [x] Updated the existing `route.test.ts`'s "exports only GET" test to also expect `PATCH`/`patchTokenFile`, matching the sibling `tokens/route.test.ts`'s convention (tolerates named helper exports, only asserts other HTTP verbs are absent) rather than the previous exact-match assertion.

## Risks & Mitigations
- Risk: `applyTokenEdits` (server, `Map`-based) and `applyEditsToPlainNode` (client, array-based) are two separate implementations of "patch a tree node" that must agree on rename-collision semantics, or the client could accept an edit the server then rejects. → Mitigation: keep both deliberately minimal (rename/value/description only, no structural edits), and treat any AC-03 test failure on either side as a signal to compare the two implementations line-by-line, not just fix in isolation.
- Risk: migrating every existing `apps/web-app` test file to Vitest as part of this feature (rather than a dedicated migration feature) touches passing, previously-reviewed test files. → Mitigation: the migration is a mechanical import/hook-rename only (no assertion logic changes), and `/sdd-implement` re-runs the full suite after Step 5 before writing any new code, so a broken migration surfaces immediately, isolated from the new feature logic.
- Risk: `jsdom` doesn't implement every browser API (e.g. `HTMLFormElement.requestSubmit`, layout/measurement APIs) — a component relying on one of those would fail under Vitest despite working in a real browser. → Mitigation: keep `EditableTokenTree`'s interactive surface to plain controlled inputs/selects and `fetch` (mocked in tests), which `jsdom` + `@testing-library/react` handle natively; flagged here in case a later feature's UI needs something `jsdom` doesn't support.
- Risk: A future token type's `$value` might need `$extensions`-style unknown fields preserved even when the type is "editable," which `serializeValue`'s identity-function approach for Dimension wouldn't generalize to. → Mitigation: not a problem for Dimension (spec defines no extension fields within `$value`); flagged here so the next token-type package (e.g. `color`) revisits whether `serializeValue` needs to merge back an unknown-fields bag, rather than assuming Dimension's identity-function approach is the general pattern.

## Estimated Complexity
High — two new packages, a new core-library capability (`serialize()`/tree editing) that several later features will depend on, a new write path with its own validation edge, the first interactive client-side state in the app, and a test-runner migration for `apps/web-app` (four new devDependencies, justified above by `node:test`'s inability to execute JSX at all).
