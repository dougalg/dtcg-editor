# Phase 0 Research: token-core Coherence Pass

## Research Task 1 — Where does type inference actually have material to work with today?

**Decision**: `classifyValue` matches a token's `$value` shape against `token-core`'s existing per-type Zod value schemas — today only `ColorValueSchema` (`color.ts`) and `DimensionValueSchema` (`dimension.ts`). It returns the single `DtcgTokenType` whose schema matches, or `undefined` if zero or more than one schema matches.

**Rationale**: `token-core` only has real, spec-conformant value schemas for 2 of the 13 DTCG types today (confirmed by reading `token-types.ts`'s `DTCG_TOKEN_TYPES` list against the actual exported `*ValueSchema`s in `index.ts` — only `Color*`/`Dimension*` exist). FR-001's "unambiguously matches exactly one of the DTCG spec's defined token types" can only be tested against schemas that actually exist; there is no principled way to test a value against a type `token-core` hasn't modeled. Designing `classifyValue` as an iteration over a registry of `(type, schema)` pairs — rather than hardcoding two `if` branches — means it automatically starts covering more types the day a schema for e.g. `fontWeight` or `duration` is added, with zero further plan/code changes to the inference logic itself. Checked for real ambiguity between the 2 existing schemas: `ColorValueSchema` is an object with `colorSpace`/`components` (or a 6-digit hex string); `DimensionValueSchema` is an object with `value`/`unit`. No overlap exists today, so FR-001's Scenario 1 (unambiguous match) is the only reachable case right now; FR-002's Scenario 2 (genuine ambiguity) has no live example yet but the design must not special-case around that — it's exercised by a synthetic third schema in the unit test suite, not skipped.

**Alternatives considered**:
- Hardcode inference only for `color`/`dimension` with no registry abstraction — rejected: locks the ambiguity-detection logic to 2 types by construction, contradicting FR-001's "any value shape that unambiguously matches" wording, and would need a second unrelated change the day a 3rd schema is added.
- Build a bespoke shape-matcher independent of the existing Zod schemas — rejected: violates Principle IV (validation lives once, at the schema); would create a second, driftable source of truth for what a `color` or `dimension` value looks like.

## Research Task 2 — What does "a single upfront resolution pass" mean given the existing immutable-tree architecture?

**Decision**: A new module `resolve-effective.ts` exports a pure function (working name `resolveEffectiveDocument(document: TokenDocument): TokenDocument`) that walks the whole tree once, top-down, threading the ancestor chain internally exactly the way `plain-node.ts`'s `toPlainNode` already does, and returns a *new* immutable tree where every node additionally carries `effectiveType: string | undefined` and `effectiveDeprecated: boolean | string | undefined` — materialized once per node, reusing the existing `resolveEffectiveType` primitive for the type/inheritance part and `classifyValue` (Research Task 1) for the inference fallback. `resolveEffectiveType`/`findNode` in `resolve-type.ts` are kept unchanged as the lower-level primitives this pass is built on (per the spec's own Assumptions section) — `edit.ts`'s `findNode` usage for locating a node during an edit is unrelated to effective-type resolution and stays as-is.

**Rationale**: `TokenNode`/`GroupNode` are `readonly` interfaces built functionally (see `edit.ts`'s `{...node, ...}` pattern) — there is no mutation path available, so "materializing a field" necessarily means producing a new tree, consistent with how every other tree transformation in this codebase already works (`applyTokenEdits`, `renameSubtreePath`). This function must be called at exactly two points to keep the "single pass, not per-call-site" guarantee real: (1) immediately after `parseTokenFile` succeeds, in `apps/web-app/lib/tokens/read.ts` (the file-read boundary), and (2) immediately after `applyTokenEdits` succeeds, in `route.ts`'s `PATCH` handler (since an edit can change a value's shape, a name, or now a declared type, any of which can change effective type/deprecation downstream). This is a call-site decision for `tasks.md`, but the plan-level contract is: any code holding a `TokenDocument`/`DtcgNode` after this feature lands can trust `effectiveType`/`effectiveDeprecated` are already correct for that document's current state, and must not call `resolveEffectiveType` directly to re-derive them (that's now the internal primitive the pass itself uses).

**Alternatives considered**:
- Fold the resolution pass into `parseTokenFile` itself (compute effective fields during the existing parse walk) — rejected: `applyTokenEdits` also needs the pass re-run after every edit batch (a rename or value edit can change effective type), and `parseTokenFile` has no reason to know about edits; keeping resolution as its own explicit step after either producer keeps `parse.ts` focused on parsing only (Principle II).
- Return a side-table (`Map<path, {effectiveType, effectiveDeprecated}>`) instead of enriching the node objects — rejected: every call site (`plain-node.ts`, `reference-index.ts`) already has the node object in hand at the point it currently calls `resolveEffectiveType(node, ancestors)`; a side-table would force those call sites to also thread a path-keyed lookup, which is more invasive than reading a field already on the object, and reintroduces the same kind of indirection the coherence pass is meant to remove.
- Rewrite all 4 call sites to stop tracking `ancestors` entirely, since the new pass makes ancestor-tracking unnecessary at read time — accepted as a natural consequence for 3 of the 4 (`plain-node.ts`, `reference-index.ts`'s `collectOccurrences`), but `reference-index.ts`'s `lookupForMode` and `route.ts`'s edit-target lookup still need `findNode` for locating a node by path in the first place (unrelated to effective-type computation), so `ancestors` tracking there doesn't fully disappear, it just stops being used for `resolveEffectiveType` calls.

## Research Task 3 — Does `$deprecated` actually inherit from ancestor groups per the DTCG 2025.10 spec, the way `$type` does?

**Decision**: Yes — treat `$deprecated` with the same precedence rule as `$type` (own declaration wins; otherwise nearest ancestor's declaration; otherwise not deprecated), and have the upfront pass compute `effectiveDeprecated` using the same ancestor-walk shape `resolveEffectiveType` already implements for `$type`, generalized to also read `deprecated` instead of `declaredType`.

**Rationale**: The DTCG 2025.10 Format spec's `$deprecated` section (designtokens.org/tr/2025.10/format/) documents `$deprecated` as inheritable the same way `$type`/`$description` are — a group marked deprecated implies every descendant is deprecated unless a descendant explicitly overrides it. This wasn't previously implemented anywhere in this codebase (today's `node.deprecated` at every read call site is the node's *own* declared value only, never ancestor-resolved — confirmed by reading `plain-node.ts` and `types.ts`), so this is a small, genuine behavior improvement bundled into the same upfront pass FR-004 already mandates, not scope creep: FR-004 explicitly names "effective `$deprecated` status" as part of what the pass must materialize, and Principle I (DTCG Spec Compliance) requires this project's model to match the spec rather than silently under-implement an inheritance rule the spec defines. This is flagged here per the Constitution Check's Principle I gate, and must be called out in the feature's PR description as a behavior change (a group-deprecated token's `effectiveDeprecated` will now read `true`/the message where it previously read the token's own `undefined`) even though it isn't one of the spec's numbered User Stories.

**Alternatives considered**:
- Treat `effectiveDeprecated` as just `node.deprecated` (no inheritance), only bundling `$type` inference into the "effective" naming — rejected: contradicts the DTCG spec's actual inheritance rule for `$deprecated`, which Principle I says must not be silently under-implemented; also contradicts FR-004's plain reading ("effective ... `$deprecated` status ... materialized ... once" implies a resolution step exists, not a pass-through of the already-present field).

## Research Task 4 — What does `@styleframe/dtcg`'s pipeline shape suggest, without adopting it as code?

**Decision**: Reuse the earlier spike's already-completed finding (`docs/research/styleframe-dtcg-spike.md`, Pass 4) rather than re-researching: the library's `parse → applyInheritance → resolveAliases` staged shape maps directly onto this feature's `parse → resolve (type/deprecated inheritance + inference) → [edit] → serialize` pipeline — the "resolve" stage this feature adds is functionally this project's hand-rolled analogue of the library's `applyInheritance` stage, generalized to also do type inference (which the library's own `classifyValue` does, per the spike). No further external research is needed for this task; the spike is the authoritative source and is cited directly in the new README (User Story 3).

**Rationale**: The backlog item and spec `Input` both point at this spike explicitly as the source of the "design-only track (b)" scope; re-deriving its findings independently would duplicate already-completed research rather than build on it, which the spike document itself was produced for.

**Alternatives considered**: N/A — re-running the spike's analysis from scratch was considered and rejected as redundant given the spike already exists and is directly cited by this feature's own spec `Input`.
