## Dependencies & Execution Order

### Phase Dependencies

- **Setup (Phase 1)**: No dependencies — start immediately
- **Foundational (Phase 2)**: Depends on Phase 1 (package must exist for token-core tests to
  eventually be consumed, though `cubic-bezier.ts`/`.test.ts` themselves only need `token-core`
  itself) — BLOCKS every user story phase, since all three need `CubicBezierValueSchema`
- **User Story 1 (Phase 3)**: Depends on Phase 2. Independently testable/shippable alone (MVP).
- **User Story 2 (Phase 4)**: Depends on Phase 2 and on `token-type.ts` existing from Phase 3
  (T012) to attach `Preview` to — not fully independent of US1's `token-type.ts` file, but the
  `Preview` component itself (T014–T017) has no code dependency on `CubicBezierEditor` and can
  be developed/tested in isolation
- **User Story 3 (Phase 5)**: Depends on Phase 2 (schema) and Phase 4 completing
  `cubicBezierTokenType`'s full shape (registration wires up the already-complete contract) —
  in practice run last since it's the end-to-end wiring step
- **Polish (Phase 6)**: Depends on all prior phases

### Parallel Opportunities

- T002 (fixture copies) can run in parallel with T001 review/finalization once T001's
  directories exist
- T008 and T009 (US1 tests) are parallel (different files)
- T014 and T015 (US2 tests) are parallel (different files)
- T021 is parallel with T020 (different files)
- T024 is parallel with nothing else in Phase 6 (it's the only [P] task there, run before T025)

## Implementation Strategy

### MVP First

1. Phase 1 (Setup) → Phase 2 (Foundational schema) → Phase 3 (User Story 1: the Editor)

   and is independently demoable even before `Preview` or host-app registration exist

   (polish) for full feature completion
