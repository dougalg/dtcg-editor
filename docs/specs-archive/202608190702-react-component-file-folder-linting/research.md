# Research: React Component File & Folder Linting

All Technical Context fields were resolvable directly from the existing codebase, the constitution, and web research into available tooling; no `NEEDS CLARIFICATION` markers remain. This document records the decisions made and the alternatives rejected.

## 1. How to detect naming/folder-placement violations

**Decision**: `@ls-lint/ls-lint` — a purpose-built, MIT-licensed filename/directory-structure linter, distributed as a prebuilt Go binary via a thin npm wrapper (no Go toolchain, no additional transitive JS dependencies). Configured entirely via a root `.ls-lint.yml`; no custom script required.

**Rationale**: The rules this feature enforces (filename casing, folder-name-matches-file-name, one-component-file-per-folder) are about the *filesystem*, not syntax inside a single file — ruled out Biome's own plugin system for that reason (see rejected alternative below). Verified `ls-lint`'s actual capabilities (not assumed) via its docs and GitHub README before committing to it:
- **PascalCase filenames** (FR-001): built-in `PascalCase` rule.
- **Folder name matches the component file's base name** (FR-003): `regex:${0}`, where `${0}` substitutes the immediate parent directory's own name into the regex pattern — confirmed via `ls-lint.org`'s rules documentation, example: `components/*: .ts: regex:${0}`.
- **Exactly one component file per folder** (FR-002, in combination with folder-per-component structure): `exists:1`/`exists:N-M` rule, restricting a matched extension to an exact or ranged count within a directory.
- **Excluding Next.js reserved files** (FR-010): the top-level `ignore:` list (confirmed example: `ignore: - node_modules`) excludes `apps/web-app/app/` outright, and/or rules are simply never declared for that path — `ls-lint` only checks paths a rule glob matches.

This is a case where Principle VIII's "better than hand-rolling" bar is clearly met: the directory-aware regex/count logic these rules need is exactly `ls-lint`'s reason for existing, and is meaningfully easy to get wrong by hand (path traversal, cross-platform separators, symlink handling) — see the Principle VIII justification in `plan.md`'s Constitution Check for the full comparison against the custom-script alternative that was the original plan for this feature.

**Alternatives considered**:
- **Custom Node script using the TypeScript compiler API** — this was the original plan for this feature (see earlier commits to this file). Rejected once `ls-lint` was found and its exact rule capabilities confirmed to cover every filename/folder requirement (FR-001–FR-003) declaratively — writing and maintaining ~150+ lines of custom filesystem-walking/regex code for a problem a tested, purpose-built tool already solves does not clear Principle VIII's bar once a suitable off-the-shelf tool is known to exist.
- **Biome Grit plugin** — rejected: confirmed Biome's Grit plugins (see `biome/*.grit` files already in this repo) operate on one file's AST at a time; they have no access to filenames or sibling/directory structure at all, so this category of rule is categorically out of their reach regardless of implementation effort.
- **`eslint-plugin-check-file`** (an ESLint plugin with similar filename/folder rules) — rejected: using it would require introducing ESLint as a second linter alongside Biome, which conflicts with this repo's constitution (Biome is the linter of record; `typescript-eslint`/ESLint are explicitly being phased out per the backlog's TypeScript v7 upgrade item, not reintroduced).
- **Content-based one-component-per-file rule** — considered and then explicitly dropped from this feature's scope entirely (not just its detection mechanism): see spec.md Assumptions. No tool — off-the-shelf or custom — was evaluated further for it once the decision was made not to build it this feature.

## 1a. Fixing the FR-004 gap surfaced by `/speckit-analyze`: co-located test files vs. the component file

**Problem found**: The rule group as originally planned (`.tsx: PascalCase | regex:${0} | exists:1`) targets the `.tsx` extension generically. Every component folder has multiple `.tsx`-suffixed files beyond the component itself once tests are counted — `SaveButton.test.tsx`, `SaveButton.a11y.test.tsx`, and `TokenTree` alone has four (`.test.tsx`, `.a11y.test.tsx`, `.generic-editor.test.tsx`, `.override.test.tsx`). `ls-lint`'s own docs describe "sub-extensions" as a distinct configuration concept from a plain extension, but the exact matching semantics for a *compound* suffix like `.a11y.test.tsx` (three dot-segments) weren't confirmed from documentation alone — this is exactly the kind of assumption `contracts/lint-diagnostics.md` already flagged as needing empirical verification during implementation, not something to guess at in this document.

**Decision**: Declare every `.tsx`-suffixed test-file variant actually present in the codebase as its own explicit sub-extension key in `.ls-lint.yml`, with a permissive rule (no case constraint, `exists` ranged generously, e.g. `exists:0-10`) — rather than relying on the generic `.tsx:` key to somehow not catch them. Concretely: `.test.tsx`, `.a11y.test.tsx`, `.generic-editor.test.tsx`, and `.override.test.tsx` each get their own key, scoped to the same `apps/web-app/components/*` / `packages/design-system/src/components/ui/*` path globs as the component rule. This must be verified against the installed `ls-lint` binary as an implementation task (not assumed correct from docs) — if sub-extension keys don't behave as expected, the fallback is `ls-lint`'s `regex` negation syntax (`!pattern`) on the `.tsx:` rule itself to explicitly exclude anything ending in `.test.tsx`/`.a11y.test.tsx`/etc. Note this problem is specific to files sharing the literal `.tsx` terminal extension — `.module.css` (a distinct top-level extension from `.tsx`) was never at risk of being caught by a `.tsx:` rule in the first place, so it needs no rule declared at all to satisfy FR-004 (an undeclared extension is simply never checked by `ls-lint`).

**Rationale**: Satisfies FR-004 ("MUST NOT flag co-located test file(s) or style file(s)") unambiguously and prevents the `exists:1` component-file-count rule from miscounting test files as extra component files, which would have made FR-012 ("zero violations after migration") unreachable — every component with more than one test file would fail immediately after migration.

**Superseded during implementation** — see §1b: empirical verification against the installed binary found this fix unnecessary. The sub-extension keys were never added to the shipped `.ls-lint.yml`.

## 1b. Empirical corrections made during `/speckit-implement` (verified against `ls-lint` v2.3.1)

Two assumptions from planning turned out to be wrong once actually tested against the installed binary — recorded here since both materially changed the shipped `.ls-lint.yml` from what §1/§1a describe.

**1. `.tsx`-suffixed test files were never at risk (§1a's fix was unnecessary).** Hands-on testing (create `Widget.tsx` + `Widget.test.tsx` + `Widget.a11y.test.tsx` in one folder, run `ls-lint -debug`) showed all files get scanned but only `Widget.tsx` is checked against a `.tsx:` rule — `ls-lint` matches extensions by exact string, not by suffix. A file literally named `.test.tsx` is a different extension from `.tsx` as far as `ls-lint` is concerned, full stop, with no sub-extension key required to achieve that. The `.ls-lint.yml` actually shipped has no `.test.tsx`/`.a11y.test.tsx`/etc. keys — FR-004 is satisfied automatically, by construction, not by an explicit exclusion.

**2. `|` between rules on one key is a logical OR, not AND — the originally planned `PascalCase | regex:${0} | exists:1` was actively wrong.** Tested directly: a file named `Widget.tsx` sitting in a folder named `Wrong` (i.e., failing the "folder name matches file" check) still passed with that combined rule, because it satisfied `PascalCase` alone and `|` accepts any one match. This would have silently let correctly-cased-but-misplaced files through — a real hole in FR-002/FR-003 enforcement, not just an untidy rule. Fixed by declaring `.dir: PascalCase` (on the folder) and `.tsx: regex:${0} | exists:1` (on the file) as separate keys — `regex:${0}` alone already forces the file's basename to exactly match its folder name, and since that folder name is independently required to be PascalCase, the file is transitively PascalCase too, with no need for a redundant case rule on the `.tsx` key.

A third, related gap found the same way: `ls-lint`'s `/*` glob only matches directories that already exist one level down, so a flat file sitting directly in the parent (sibling to a valid component folder) was invisible to the `apps/web-app/components/*` rule entirely — confirmed by placing a stray flat file next to an already-correct component folder and seeing it pass silently. Fixed by adding a bare (non-glob) directory key — `apps/web-app/components: { .tsx: exists:0 }` — forbidding any `.tsx` file directly in the parent, independent of the `/*` rule.

**Consolidation (post-implementation, on request)**: `apps/web-app/components` and `packages/design-system/src/components/ui` need byte-for-byte identical rules. Rather than repeating each rule block twice, `ls-lint`'s brace-expansion glob syntax (`"{a,b}"`, confirmed via its own docs example `packages/*/{src,__tests__}` and verified hands-on that it both indexes and enforces correctly) combines both locations into one rule block each: `"{apps/web-app/components,packages/design-system/src/components/ui}"` and the matching `/*` variant.

## 2. Where the config lives and how it's wired into `pnpm lint`

**Decision**: A single root `.ls-lint.yml`. Add a `"lint:filenames"` script to root `package.json` (`"ls-lint"`, `ls-lint`'s own CLI invocation, no flags needed since config is auto-discovered from `.ls-lint.yml` at the invocation root). Add a `"//#lint:filenames"` entry to `turbo.json`'s `"lint"` task `dependsOn`, alongside the existing `"//#lint:root"`.

**Rationale**: This repo already has a working pattern for "a repo-wide root check that isn't a per-package build target" (`//#lint:root`, running Biome against root-level `.cjs` config files). Adding a second root-only check is the smallest change that gets this enforced under the same `pnpm lint`/CI umbrella with zero new pipeline stages. Critically, `//#lint:root` and the new `//#lint:filenames` become two independent entries in the same `dependsOn` array — neither depends on the other — so Turborepo's scheduler runs them concurrently rather than one after the other; `pnpm lint` stays a single command and its wall-clock time is governed by the slowest task in the graph, not the sum of all of them.

**Alternatives considered**:
- **A per-package `lint` script addition** (e.g. running `ls-lint` separately inside `apps/web-app`'s and `packages/design-system`'s own `lint` scripts) — rejected: the folder-name-match rule (FR-003) and future scope growth benefit from one config file with visibility across the whole repo tree, matching how `.ls-lint.yml`'s path-glob keys (e.g. `apps/web-app/components/*`, `packages/design-system/src/components/ui/*`) are naturally expressed as one file, not fragments duplicated per package.
- **Pre-commit-only (husky) enforcement, no CI gate** — rejected: FR-006 requires it run under the single `pnpm lint` command (both local and CI-enforced already); `pnpm lint` itself is not currently husky-gated, so mirroring the existing `lint:root`/CI path (not adding a new local-only hook) matches current enforcement points.

## 3. One-component-per-file rule: dropped from scope

**Decision**: Not implemented in this feature, by explicit product decision after the `ls-lint`-vs-custom-script tradeoff was discussed. Constitution Principle X's "a file MUST NOT export more than one component" clause remains unenforced by any tooling; `card.tsx`'s 8-components-in-one-file pattern remains as-is.

**Rationale**: `ls-lint` (or any filename/directory linter) fundamentally cannot express this rule — it requires reading file contents to know which components a file exports, which is outside what any filename-based tool can ever do. Building a second, separate custom tool (the TypeScript-compiler-API script from the superseded plan) solely for this one rule, after already deciding not to hand-roll the filename/folder rules `ls-lint` now covers, was judged not worth the added maintenance surface for a single rule — a smaller, more consistent tooling footprint (one dependency, one config file) was preferred over a hybrid of one config-driven tool plus one custom script.

**Alternatives considered**:
- **Prefix-based compound-component heuristic in a custom script** (the approach designed in an earlier iteration of this plan, before this decision) — superseded; the design remains available in this file's git history if this rule is picked up as separate future work.
- **Keep the rule but scope the custom script to only this one check** — rejected: still requires writing, testing, and maintaining a bespoke AST-parsing script for a single rule, which is the exact overhead this feature is otherwise avoiding by using `ls-lint`.

## 4. Migration mechanics

**Decision**: A one-time, scripted bulk migration (not manual file-by-file editing) — a throwaway Node script that, for each existing component file: computes its target PascalCase path, `git mv`s the component file and every co-located test/style file into the new per-component folder, then rewrites every relative import referencing the old path across the repo (via a repo-wide grep-and-replace over `.ts`/`.tsx` files). This script is not part of the shipped feature (it is not `ls-lint`-related tooling); it is a one-time migration aid, run once and discarded.

**Rationale**: ~28 component files move in this migration; a scripted rename-and-import-fix is far less error-prone than hand-editing that many import paths. Confirmed via repository search that no code outside `apps/web-app/components/*` and `packages/design-system/src/components/ui/*` currently imports design-system components by path (the package isn't wired up to any consumer yet beyond its `package.json`/`next.config.ts` dependency declaration), and no cross-imports exist between `packages/design-system/src/components/ui/*` files themselves — which keeps this migration's blast radius to import statements within `apps/web-app/components/*` (which do reference each other, e.g. `TokenTree.tsx` → `TreeGroupNode.tsx`) plus each file's own test/story imports. Running `ls-lint` after migration (exit code `0`) is the acceptance check that the migration is complete, per FR-012.

**Alternatives considered**:
- **Manual migration** — rejected: higher risk of a missed import at this file count, no reason to prefer it over a scripted move given the script is a one-time throwaway tool, not part of the shipped lint check itself.
- **Gradual/opt-in migration (leave both conventions live, migrate incrementally)** — rejected by the user's explicit choice earlier in scoping: migration is delivered as part of this feature, not deferred (see spec.md Assumptions).

## 5. Hooks/lib naming scope (added after `/speckit-analyze`, per explicit request)

**Decision**: Add two more rule groups to the same `.ls-lint.yml`: `apps/web-app/hooks/*: .ts/.tsx: camelCase` and `apps/web-app/lib/**: .ts/.tsx: kebab-case` (recursive, since `lib/` has nested subdirectories like `lib/token-editors/`, `lib/tokens/`). No migration task needed — confirmed by direct inspection (`find apps/web-app/hooks -type f`, `find apps/web-app/lib -type f`) that every one of the ~2 hooks files and ~24 lib files already complies with its respective convention today.

**Rationale**: These are pre-existing, already-consistent conventions this repo already follows but has never enforced — the same "will eventually drift without enforcement" problem User Story 1 solves for components, applied to two more directories, using the same tool and config file already being added for this feature. Scoped narrowly to these two directories only (not "any `hooks/`or `lib/` anywhere in the repo") since a repo-wide search confirmed no other package has directories of this kind today; a future new one would need its own explicit `.ls-lint.yml` addition, same as any other new rule scope, rather than this rule silently expanding to cover it.

**Alternatives considered**:
- **Skip this scope, leave it as a documentation-only convention** — rejected per explicit user request to add it as enforced scope now, while the same tool/config file is already being introduced for this feature.
- **A generic recursive rule matching "any hooks/lib directory anywhere"** — rejected: over-generalizes for a convention only confirmed to exist in these two specific locations today; scope should track what's actually been verified, not extrapolate to hypothetical future directories.

## 6. Post-implementation scope expansion: `packages/token-editor-color`/`token-editor-dimension`, denesting `design-system`'s `ui/`, and the `**` glob's phantom-violation bug

**Trigger**: A post-implementation request to consolidate the (by-then-duplicated) `apps/web-app/components` / `packages/design-system/src/components/ui` rule blocks led to checking whether other `components/` directories existed in the repo — found `packages/token-editor-color/src/components/` and `packages/token-editor-dimension/src/components/`, both following the exact same flat, non-PascalCase pattern this feature was already fixing elsewhere, and never brought into scope. Extended to cover them, per explicit request, rather than leave a known gap.

**Decision — denesting**: `packages/design-system/src/components/ui/*` moved up one level to `packages/design-system/src/components/*` (e.g. `ui/Button/Button.tsx` → `Button/Button.tsx`), and `package.json`'s `"./components/*": "./src/components/ui/*"` export updated to `"./src/components/*"`. This makes `packages/design-system/src/components` structurally identical to `packages/token-editor-color/src/components` and `packages/token-editor-dimension/src/components` — all three are now `packages/<name>/src/components/<PascalComponent>/`, letting one glob pattern cover all of them plus `apps/web-app/components`.

**Decision — glob pattern**: `"{apps/web-app/components,packages/*/src/components}"` (and the `/*` variant), not a `**/components` recursive glob. **A real bug was found and must be avoided**: tested `**/components` combined with an `ignore: [dist]` (or `ignore: ["**/dist"]`) entry, and confirmed `ls-lint` still produces a *phantom* violation for the ignored path — `ignoreme/components/Foo failed for .tsx rules: exists:1 (found 0)` — even though the actual file walk correctly skips it (confirmed via `-debug`: the ignored directory never appears in the "lint" section, only in the "ls index" rule-matching section). This is because `ls-lint`'s glob-based rule-index construction runs independently of, and prior to, ignore-filtering of the file walk — an ignored directory that still structurally matches a `**` pattern gets indexed as "rules apply here," and since it's then never scanned, `exists:1` sees zero matching files and fails. Every package here gets a `dist/src/components/` build-output mirror on `pnpm build`, so `**/components/*` would have broken `pnpm lint` after every build. The narrower `packages/*/src/components` pattern avoids this entirely by construction — it can never structurally match `packages/*/dist/src/components` (the segment immediately after `packages/*` must literally be `src`), so no `ignore` entry is needed for `dist` at all in relation to this rule. Verified with a full `rm -rf dist && pnpm build && pnpm lint` cycle against the real repo, not just the isolated reproduction.

**Rationale**: Denesting removes a nesting level (`ui/`) that existed only to group `design-system`'s components, and which duplicating in the lint glob's design would have provided no value once every component location follows an identical convention — one glob pattern is simpler than a hand-maintained brace-expansion list, and automatically covers a future `packages/<new-package>/src/components/` without a config change. The `**`-glob bug, however, is the reason a fully generic "match every `components/` dir anywhere" approach was rejected in favor of the narrower, still-somewhat-generic `packages/*/src/components` pattern — confirmed empirically to avoid the bug rather than assumed safe.

**Alternatives considered**:
- **`**/components/*` (fully recursive)** — rejected: proven to produce phantom violations against ignored `dist/` build-output directories, which exist in every package here and are regenerated on every `pnpm build`.
- **Keep `packages/design-system/src/components/ui/` nested, add `packages/token-editor-color/src/components` and `packages/token-editor-dimension/src/components` as two more explicit brace-expansion entries (4 total)** — rejected in favor of denesting once it became clear a single `packages/*/src/components` pattern could replace 3 of the 4 entries; the explicit-list approach still works and was the fallback if denesting had been rejected, but is more entries to maintain for no benefit once the structural inconsistency (`ui/` in one location, not in others) was itself a discrepancy worth removing.
