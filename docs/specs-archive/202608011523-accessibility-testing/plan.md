# Implementation Plan: Accessibility Testing

## Overview

Add two new, additive test suites to `apps/web-app` — no production code behavior changes are anticipated up front, though real WCAG 2.2 AA violations found along the way must be fixed as part of this feature (see Risks below), not deferred.

1. **Component-level**: a second Vitest "project" (alongside the existing jsdom project, in the same `vitest.config.ts`) running in a real Chromium instance via `@vitest/browser`'s Playwright provider. `*.a11y.test.tsx` files, co-located with the component they test (per this repo's testing convention), import `axe-core` directly and run it against the rendered component.
2. **Page/flow-level**: a new `@playwright/test` suite in a new `apps/web-app/e2e/` directory, driving the real built app (`next build && next start`) to check whole-page axe results and keyboard-only navigation/focus order across the browse → open → edit → save flow.

Both suites are wired into `apps/web-app`'s existing `pnpm test` script, so `turbo run test` / CI's existing `pnpm test` step enforces them with no `turbo.json` changes.

## Architecture Decisions

- **Vitest Browser Mode, not a second unrelated tool, for component-level checks.** `@vitest/browser` (Playwright provider, Chromium) renders components in a real browser inside the _same_ `vitest.config.ts`/`pnpm test` the project already has, via Vitest's `test.projects` array — one project keeps today's jsdom config untouched, a new project turns on `browser.enabled`. This is what makes axe-core's `color-contrast` rule (and other rules needing real `getComputedStyle`/layout) actually work — jsdom cannot provide this, confirmed empirically per `feature.md`.
- **`@testing-library/react`'s `render`/`screen` work unchanged in browser mode — no new rendering-library dependency.** Testing Library queries the DOM directly; it has no jsdom-specific dependency, only on `document`/DOM APIs, which Vitest Browser Mode provides for real. This avoids adding `vitest-browser-react` or similar.
- **axe-core is called directly inside the browser-mode test file — no bridge/integration package for the Vitest side.** Vitest Browser Mode test code itself executes _inside_ the real browser (unlike Playwright, where test code runs in Node and talks to the browser over CDP), so a component test simply does `import axe from "axe-core"; const results = await axe.run(container, { runOnly: { type: "tag", values: WCAG_22_AA_TAGS } });` with no injection step needed.
- **For Playwright, axe-core is injected via a small hand-rolled helper, not `@axe-core/playwright`.** `axe-core` ships a ready-to-inject `axe.min.js` browser bundle at its package root (the same file `@axe-core/playwright` reads internally). A ~20-line `apps/web-app/e2e/support/axe.ts` helper (`page.addScriptTag({ content: readFileSync(require.resolve("axe-core/axe.min.js"), "utf-8") })` then `page.evaluate(() => axe.run(...))`) does the same job without a new dependency, mirroring this repo's existing "small adapter module, no wrapper library" pattern (e.g. `lib/platform/node-fs.ts`).
- **A shared `WCAG_22_AA_TAGS` constant, not a duplicated tag list per test file.** axe-core's WCAG tags are additive per spec version (`wcag2a`, `wcag2aa`, `wcag21aa`, `wcag22aa` must all be listed together to get full "AA and below" coverage) — one wrong/incomplete list in some test file would silently under-check. Lives at `apps/web-app/lib/a11y/wcag-tags.ts` (a plain constant, not a mock, so it sits in `lib/` rather than the new `e2e/` tree) and is imported by both the component-level `*.a11y.test.tsx` files and the Playwright suite.
- **A new top-level `apps/web-app/e2e/` directory, an explicitly flagged deviation from "tests live alongside code."** Playwright tests exercise composed pages/flows spanning multiple components and routes, not one single module they'd sit next to — same reasoning `feature.md`'s Non-Functional Requirements already called out. `e2e/support/` holds the shared `axe.ts` helper; this is also a deliberate, flagged deviation from the "mocks are hand-rolled per-file, no shared test-utility module" convention — that convention targets I/O _mocks_ for unit tests, whereas this is a real-dependency bridge shared by multiple page-level specs, where the drift risk of _not_ sharing it (several slightly different axe-injection implementations) is the bigger problem.
- **Playwright's `webServer` runs the production build, and skips rebuilding in CI.** `command: process.env.CI ? "pnpm run start" : "pnpm run build && pnpm run start"` — CI's existing "Build" step (in `.github/workflows/ci.yml`, before "Test") already produced a fresh `apps/web-app/.next`, so re-running `next build` in the same job would waste CI time; a local `pnpm test` run has no such guarantee, so it builds first. Playwright polls `url` for readiness (no arbitrary sleep, no flakiness), resolving `feature.md`'s deferred "dev vs prod server" open question in favor of testing the real production bundle.
- **The save-flow E2E test backs up and restores the exact fixture file it edits, rather than using a temp/ephemeral tokens directory.** `dtcg-editor.config.mts`'s `tokensDir` is resolved via a static, build-time top-level import (2026-07-29 Architecture Decision in `docs/project.md`) specifically so `extensions`' component references are statically resolvable — there is no supported way to point a single test run at an ephemeral tokens directory without changing that established config-loading architecture, which is out of scope here. The test instead snapshots `sample_data/spacing_scale.tokens.json`'s exact bytes before running and restores them in `test.afterEach` (which Playwright guarantees runs even on test failure/timeout), keeping the repo's committed fixture byte-identical after every run, local or CI.
- **Only Chromium is installed and tested**, for both the Vitest Browser Mode provider and the Playwright suite. Cross-browser (Firefox/WebKit) coverage is deferred — out of scope per `feature.md` — keeping CI time bounded.

## New Dependencies (Minimal Dependencies sign-off)

All five are new `devDependencies` in `apps/web-app/package.json` only.

| Dependency                   | Why no built-in/hand-rolled alternative works                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `@vitest/browser`            | The only way to run this repo's existing Vitest test files inside a real browser instead of jsdom; required for axe-core's rendering-dependent rules (e.g. `color-contrast`) to produce accurate results.                                                                                                                                                                                                                                                                                                                          |
| `@vitest/browser-playwright` | **Deviation from the original sketch below** (discovered at implementation time): in the installed `vitest@^4.1.10`, `browser.provider` is no longer a bare string like `"playwright"` — it must be the `playwright()` factory imported from this separate package, per that version's own `BrowserConfigOptions` type definitions. Confirmed by reading the installed `.d.ts` files directly.                                                                                                                                     |
| `playwright`                 | The actual browser-automation engine — used both as `@vitest/browser`'s provider and to drive the standalone Playwright suite. Hand-rolling browser automation/CDP control is infeasible.                                                                                                                                                                                                                                                                                                                                          |
| `@playwright/test`           | Playwright's own test runner (fixtures, `webServer` lifecycle management, parallelism) — needed for the page-level/keyboard-navigation suite (FR-02/FR-03); distinct package from the `playwright` driver above.                                                                                                                                                                                                                                                                                                                   |
| `axe-core`                   | The actual WCAG rule-checking engine (~90+ WCAG success-criteria checks). Hand-rolling this is clearly infeasible — this is the one dependency both new suites are built around. No wrapper/integration package is added on top of it (see Architecture Decisions above: the Vitest side calls it directly, the Playwright side uses a hand-rolled ~20-line injection helper instead of `@axe-core/playwright`). Needed starting in Step 1, not just Step 2, since the component-level `*.a11y.test.tsx` files import it directly. |

### Step 6: Fix any real violations found

- [x] Ran all four Step 1 component-level test files locally; found and fixed two real, non-tooling issues:
  - **`color-contrast` (WCAG 1.4.3) in `TokenTree.a11y.test.tsx`**: `.fieldLabel` in `apps/web-app/components/TokenTree.module.css` used `color: var(--foreground); opacity: 0.5`, which computed to `#808080` on `#ffffff` — a 3.94:1 ratio, below the 4.5:1 AA minimum. Fixed by replacing the opacity trick with a new `--muted-foreground` CSS custom property (`#595959` light / `#a8a8a8` dark, both >7:1 against `--background` in their theme — verified numerically, not eyeballed), added to `apps/web-app/app/globals.css` alongside the existing `--foreground`/`--background`/etc. variables, following the same per-theme-variable convention as the 2026-07-28 `--accent` decision.

Fixed via the `a11y` project's `define: { "process.env": {} }` (see Step 1 above), which is a build-time config fix, not a production code change.

## Risks & Mitigations

- **Risk**: axe-core surfaces real, pre-existing violations once the suites actually run (e.g. an ARIA-role/contrast issue nobody had tooling to catch before) → **Mitigation**: Step 6 above is a required step, not optional cleanup; budget implementation time for it, since AC-04 (CI fails the build on violations) would otherwise be trivially defeated by leaving known violations in place.
- **Risk**: Chromium download (~150 MB via `playwright install`) adds real time to every CI run → **Mitigation**: cache `~/.cache/ms-playwright` (Step 5); only Chromium (not Firefox/WebKit) is installed at all.
- **Risk**: A crashed/killed test process (not just a failing assertion) could skip `test.afterEach`'s fixture restore, leaving `sample_data/spacing_scale.tokens.json` modified → **Mitigation**: `afterEach` covers the common case (assertion failures, timeouts); as a cheap defensive backstop, CI's "Test" step can be followed by a `git diff --exit-code sample_data` check to fail loudly (not silently commit) if a fixture was left dirty — add this as a small follow-up if it's ever actually tripped, rather than pre-building it speculatively now.
- **Risk**: `vitest@^4.1.10`'s `test.projects` API shape may differ from what's sketched in Step 1 → **Mitigation**: Step 1 explicitly calls out verifying against the installed version's own types/docs before writing the config, rather than assuming the sketch is exact.

## Estimated Complexity

**Medium.** No production architecture changes and no changes to `token-core`/other packages — this is additive test tooling within `apps/web-app` only. The complexity is in correctly wiring two different real-browser test runners (Vitest Browser Mode and Playwright) side by side without one breaking the other's config, plus Step 6's open-ended "fix whatever axe actually finds," which can't be sized precisely until the suites run for the first time.
