- [ ] Make `token-core` resolver-aware — a definite, wanted refactor (not a "maybe," unlike most items on this list), and bigger than one function: today, everything about the DTCG Resolver Module (`tokens.resolver.json`) is app-specific and read-only. `apps/web-app/lib/tokens/resolver-file.ts` only *parses* a resolver file (via injected file I/O, scoped to "the first modifier entry only" per its own comment) into an app-local `ResolverModes` shape, and `reference-index.ts`'s `lookupForMode` does the actual mode-composition/selection against that. None of this is exposed as an editable, spec-conformant concept the way tokens themselves now are (`parseTokenFile`/`applyTokenEdits`/`serializeTokenFile`). The wanted end state: `token-core` gains an equivalent parse/edit/resolve/serialize surface for resolver files themselves — parsing `tokens.resolver.json` into a typed model, editing it (adding/removing sets, modifiers, contexts, sources) the same ordinary way `TokenEdit` edits a token, and the mode-composition algorithm (pick the definition matching a requested mode, else fall back per spec) as a first-class exported function — not just the one narrow case (`lookupForMode`) filed here previously. **Explicitly does NOT mean adding filesystem/directory-scanning to `token-core`** — it stays exactly as file-I/O-free as it is today (see its `README.md`'s "What this package deliberately does not do"); the host app still reads/writes raw resolver-file text and supplies the multi-file document set, `token-core` only ever transforms in-memory data, same division as the existing token pipeline. Also explicitly in scope: **simplifying the user-facing interface for configuring modes/resolvers**, which today requires the user to already understand DTCG's own resolver vocabulary (`resolutionOrder`, `"set"` vs `"modifier"` entries, `contexts`) to hand-author or reason about `tokens.resolver.json` at all — the current app has no dedicated UI for this, only the read-only consequence of it (which mode's definition wins). This needs real design work on what a non-spec-fluent user actually needs to express ("light and dark themes," "a brand override"), not just an API-shape decision — likely warrants its own `speckit-specify` pass rather than folding into an existing worktree, given its scope (parsing + editing + resolution semantics + a genuinely new UI surface). Raised while reviewing `008-token-core-coherence`'s effective-field-resolution work (2026-08-26).
