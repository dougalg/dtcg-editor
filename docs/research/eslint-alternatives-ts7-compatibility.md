# ESLint alternatives and TypeScript 7 compatibility: is switching away from ESLint/typescript-eslint better than the TS6-alias workaround?

## Distilled rationale

Of the two realistic non-ESLint options, **Biome** and **oxlint** solve the TS7 problem in structurally different ways, and only one of them is a natural fit. Biome deliberately avoids the TypeScript compiler entirely — it's building its own from-scratch type inference engine ("we think it is important to implement our own type synthesiser," per its own type-aware-linting tracking issue) specifically so it never has to touch `tsc`'s API at all, TS7 or otherwise — but that engine is still early (2 of ~22 planned type-aware rules landed as of this research) and covers a small fraction of typescript-eslint's ~61 type-aware rules. **oxlint**, via its `tsgolint` companion, isn't merely "unaffected" by TS7's API removal — it's _built directly on `typescript-go` (tsgo)_, the same Go compiler that TypeScript 7 itself ships as, explicitly targets "TypeScript 7 (codenamed Project Corsa)," and version-locks its releases to TS7 point releases. It already covers 59 of 61 typescript-eslint type-aware rules and runs 12–18x faster. Both tools, however, hit the same real wall for dtcg-editor specifically: neither has a native equivalent of ESLint's `no-restricted-syntax` with arbitrary esquery attribute selectors — the exact mechanism this repo's own `eslint.config.mjs` files use to enforce the Dependency-Injection-for-I/O-Platform-Externalities architectural constraint (banning bare `Date.now()`, `new Date()`, `Math.random()`, `crypto.randomUUID`/`getRandomValues`, `process.exit`, `console.*`, and `process.env` reads outside designated adapter files). `no-restricted-imports` and `no-restricted-globals` — the repo's other two custom-rule categories — _do_ have native equivalents in both tools, so only one of the three rule families is actually at risk. Given that the TS6-alias workaround requires zero rule-migration effort and keeps 100% of the existing lint configuration (including `eslint-config-next`) working unchanged, it remains the better **near-term** choice; but oxlint/tsgolint is worth a genuine look as a _supplementary_, TS7-native fast pass later, not dismissed as "just another incompatible tool."

## Sources

1. **Biome — 2026 Roadmap blog post** — https://biomejs.dev/blog/roadmap-2026/
   States Biome shipped, in 2025, "type-aware lint rules that don't rely on the TypeScript compiler" via its own inference engine (sponsored by Vercel); the 2026 roadmap itself prioritizes HTML stabilization, cross-language linting, SCSS, and LSP work — no stated 2026 plan to expand type-aware rule coverage or any TS7-specific messaging.

2. **Biome issue #3187, "Type-aware linter" (umbrella tracking issue)** — https://github.com/biomejs/biome/issues/3187
   Primary source for Biome's design decision: "This is why we think it is important to implement our own type synthesiser," explicitly rejecting the TypeScript Compiler API approach on performance/AST-incompatibility grounds; states the synthesizer "doesn't need to be perfect... even a rudimentary type synthesiser could be valuable." As of this research, tracked progress shows 2 of ~22 planned type-aware rules (`useAwaitThenable`, `noFloatingPromises`, `noForInArray`, `noDuplicateLiteralEnumMembers`, etc.) implemented — i.e. Biome's type-aware coverage is structurally immune to the TS7 API-removal bug (it never calls into `tsc`'s JS API at all) but is far from feature-complete versus typescript-eslint's rule set.

3. **Biome docs — `noRestrictedImports`** — https://biomejs.dev/linter/rules/no-restricted-imports/
   Confirms Biome ships a native rule directly equivalent to ESLint's `no-restricted-imports` (module/import-name denylisting with custom messages) — one of the two rule categories in dtcg-editor's configs that has a drop-in Biome equivalent.

4. **Biome docs — `noRestrictedGlobals`** — https://biomejs.dev/linter/rules/no-restricted-globals/
   Confirms a native rule equivalent to ESLint's `no-restricted-globals` (deny specific global identifiers, e.g. `fetch`, with custom messages) — the second of dtcg-editor's three custom-rule categories with a drop-in Biome equivalent. Not enabled by default; must be turned on and configured, same as in ESLint.

5. **Biome recipes — "GritQL Plugins"** — https://biomejs.dev/recipes/gritql-plugins/
   Shows GritQL (Biome's own pattern-matching DSL, shipped 2.4+) can express custom AST-pattern rules with `register_diagnostic()` and custom messages/severities, e.g. banning specific import sources or call patterns. This is capable of expressing dtcg-editor's `no-restricted-syntax` selectors (`Date.now()`, `new Date()`, `Math.random()`, `crypto.randomUUID`/`getRandomValues`, `process.exit`, `console.*`, `process.env`) — but each selector would need to be **rewritten from an esquery attribute selector into a new DSL**, not ported as a config string; this is real, non-trivial migration effort, not a config swap.

6. **oxc.rs docs — "Type-Aware Linting"** — https://oxc.rs/docs/guide/usage/linter/type-aware.html
   States plainly: "Type-aware linting is powered by `typescript-go`" — i.e. it does not depend on the npm `typescript` package or its (now-removed) JS Compiler API at all. States "TypeScript 7.0+ is required" for type-aware linting, and that legacy `tsconfig` options tied to pre-7.0 behavior aren't supported. Confirms 59 of 61 typescript-eslint type-aware rules are covered.

7. **`oxc-project/tsgolint` (GitHub repo README)** — https://github.com/oxc-project/tsgolint
   Primary source for tsgolint's TS7-native design: "using typescript-go for full compatibility with the TypeScript type system," and explicitly "tsgolint is built directly on TypeScript 7, so its versions track the TypeScript release they support" (e.g. release `v7.0.2001` — first three components are the TypeScript version, remainder is tsgolint's own patch number). This is a materially different relationship to TS7 than "happens to still work" — tsgolint requires and is versioned against TS7 specifically, and states it targets "TypeScript 7 (codenamed Project Corsa)."

    (Re-checked for this follow-up, corroborating the prior research doc's finding.) Remains open, labeled as blocked by an external API; the architectural blockers are unchanged (ESLint's synchronous parser interface vs. tsgo's expected async/WASM consumption model; AST/type-information transport design still unresolved). 14. **`denoland/deno_lint` (GitHub repo) and Deno official docs — "Linting and formatting"** — https://github.com/denoland/deno_lint and https://docs.deno.com/runtime/lint_and_format/
    `deno_lint` is a Rust crate that is not Deno-specific and can in principle be embedded elsewhere, but it ships **syntax-only** rules — Deno's own documentation directs users wanting type-aware TypeScript linting to add `typescript-eslint` on top, i.e. Deno's own tooling doesn't solve the type-aware/TS7 problem itself. Standalone use from a Node/npm project (like dtcg-editor) requires an unofficial third-party wrapper (`@node-rs/deno-lint`), not a first-party supported integration. Given no first-party type-aware story and no first-party Node integration, this is not treated as a serious option and no further time was spent on it, per the research brief's own guidance.

15. **dtcg-editor repo state** — `eslint.config.mjs`, `apps/web-app/eslint.config.mjs`, `docs/project.md` (read directly, 2026-08-02)
    Confirms the exact shape of the constraint at risk: the root config bans `Date.now()`, `new Date()`, `Math.random()`, `crypto.randomUUID`/`getRandomValues` via `no-restricted-syntax` selectors (applies repo-wide to `packages/*`); `apps/web-app/eslint.config.mjs` adds `process.exit`, `console.*` member access, and `process.env` reads to the same `no-restricted-syntax` array, plus `no-restricted-imports` (banning direct `node:fs`/`node:fs/promises` imports outside `lib/platform/node-fs.ts`) and `no-restricted-globals` (banning bare `fetch` outside `useSaveTokenEdits.ts`), with a system of per-file override blocks turning specific selectors back off at each of the DI architecture's designated composition-root/adapter files. `docs/project.md`'s Approved Dependencies section states `eslint-config-next` "is pulled in automatically by Next's scaffolding and kept as the standard pairing for a Next.js app," and that ESLint + `typescript-eslint` was chosen specifically because "`tsc` has no flag that bans explicit `any`."

## Net takeaway

**The TS6-alias workaround remains the better near-term choice.** It requires zero rule-migration effort — both `eslint.config.mjs` files, including every `no-restricted-syntax`/`no-restricted-imports`/`no-restricted-globals` selector enforcing the Dependency-Injection-for-I/O constraint and every per-file override, keep working completely unchanged, as does `eslint-config-next`. A full switch to either alternative is not a like-for-like swap:

- **Biome** would keep `no-restricted-imports` and `no-restricted-globals` working natively, but its type-aware linting is still early (a small fraction of typescript-eslint's rule coverage today) and its `no-restricted-syntax`-equivalent constraints would need to be **rewritten from esquery selectors into GritQL**, a new pattern-matching DSL — real migration and re-verification work, not a config change. It also has no bundled Next.js-specific rule set comparable to `eslint-config-next`.
- **oxlint + tsgolint** is the more interesting long-term candidate precisely because it isn't just "unaffected" by TS7's API removal — `tsgolint` is _built on_ `typescript-go`, the actual engine TS7 ships as, and is versioned in lockstep with TS7 releases. It already covers 59/61 of typescript-eslint's type-aware rules at 12–18x the speed, and has a native (opt-in) `nextjs` plugin and React-hooks coverage. But it has **no native equivalent of `no-restricted-syntax`** at all — not a documented rule, and its own maintainers, when asked directly, pointed to writing a bespoke local JS plugin instead. That's the one real, concrete regression a full oxlint switch would introduce today: exactly the rule family this repo invented itself to enforce its architectural DI constraint.

**Recommendation:** stay on the TS6-alias workaround to unblock lint under TS7 now. Treat a full ESLint/typescript-eslint retirement as premature — the migration cost (rewriting or hand-rolling 4–7 restricted-syntax selectors per config, verifying they still fire/don't-fire identically, and replacing `eslint-config-next`'s automatic bundling) isn't justified just to route around a well-precedented, temporary, Microsoft-published compatibility shim. The one thing worth a follow-up spike, separate from this decision, is adding oxlint/tsgolint as a **supplementary** fast type-aware pass alongside the aliased ESLint setup (oxlint catches its 59/61 rule set at native TS7 speed; ESLint-on-TS6-alias keeps enforcing the custom DI rules and anything oxlint doesn't cover) — that captures oxlint's genuine TS7-native advantage without betting the DI enforcement on a rule category neither alternative tool currently supports.
