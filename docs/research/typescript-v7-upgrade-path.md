# TypeScript v7 upgrade: wait on Next.js, or move to Astro?

## Distilled rationale

The backlog note (2026-07-27) treated the TS7 upgrade as flatly blocked on both Next.js and `@typescript-eslint`. That's now half-stale: **Next.js shipped a working (if experimental) TS7 path in stable `16.2.12`** — the exact version dtcg-editor is pinned to — two days before the note was written, via `experimental.useTypeScriptCli`. The build failure quoted in the backlog note ("TypeScript 7.0.2 does not provide the compiler API required by Next.js") is Next.js's own *intended* error message for when TS7 is installed **without** that flag enabled — not evidence the version is unsupported. `@typescript-eslint`, however, is a harder and *framework-independent* blocker: its peer range (`>=4.8.4 <6.1.0`) excludes TS7 outright, the maintainers closed the TS7 tracking issue as "not planned," and the root problem — no stable TypeScript 7 Compiler/Language-Service API — is upstream of typescript-eslint, Next.js, and Astro alike. Astro is not meaningfully closer: `@astrojs/check` (Astro's own type-checker) and `@astrojs/language-server` depend on the same now-removed Strada API, Astro's own TS7/tsgo tracking discussion has zero maintainer replies since March 2026, and Astro would *still* carry the same blocked `@typescript-eslint` if the repo kept ESLint (which it would). Switching frameworks does not unblock the actual gating dependency.

## Findings

### (a) Next.js TS7 support — per `vercel/next.js` discussion #95633 and related PRs/docs

- Discussion #95633 (opened by `abhishekmardiya`, Jul 9 2026) reported that after installing `typescript@7.0.2`, Next.js aborted `next build`/`next dev` claiming TypeScript was "not installed." Root cause: TypeScript 7.0's npm package deliberately dropped `lib/typescript.js` — the JS Compiler API Next.js used to detect and drive TypeScript — leaving only a `tsc.js` shim over the native Go binary.
- Next.js collaborator `icyJoseph` replied the same day that a real fix wasn't yet actionable and pointed at an interim workaround: alias `typescript6` alongside `typescript@7` via npm (`"typescript": "npm:@typescript/typescript6@6.0.1"`), reporting a build-time drop from ~900ms to ~300ms with the native binary doing the heavy lifting.
- The next day (Jul 10), `icyJoseph` marked the discussion answered: PR #95639 (`timneutkens`) had landed on canary, adding an **experimental flag**, `experimental.useTypeScriptCli`, that makes `next build` spawn the project-local `tsc` CLI directly instead of loading the JS Compiler API — sidestepping the missing-API problem entirely.
- PR #95831 (`lukesandberg`, merged Jul 23 2026) backported that flag plus follow-up fixes (tsconfig path resolution without `baseUrl`, a `SIGSEGV`/`SIGABRT` crash fix, signal/termination handling, spinner support) from canary to the `next-16-2` stable line. This backport is what shipped as **Next.js `16.2.12`, published 2026-07-25** — the version already pinned in `apps/web-app/package.json`.
- Confirmed against the current official Next.js docs (both dated/versioned `16.2.12`, last updated 2026-07-23):
  - [`useTypeScriptCli` config reference](https://nextjs.org/docs/app/api-reference/config/next-config-js/useTypeScriptCli): "The `experimental.useTypeScriptCli` option makes `next build` run the project-local `tsc` command instead of loading the TypeScript JavaScript compiler API... it enables TypeScript 7 support while its JavaScript API is unavailable." Explicitly still labeled experimental / "not recommended for production."
  - [TypeScript config docs, "Using TypeScript 7" section](https://nextjs.org/docs/app/api-reference/config/typescript#using-typescript-7): confirms the flag is **opt-in only** — "If you install TypeScript 7 without enabling `experimental.useTypeScriptCli`, `next build` exits with instructions to enable the option..." This is exactly the error the backlog note captured; it reflects a missing flag, not a hard incompatibility.
  - Caveats: CLI-mode diagnostics are raw `tsc` output (no Next.js-specific code frames/route error rewriting); the CLI type-checks the *whole* project selected by `tsconfig.json` (including test files), not just Next's normal scoped set.
- Timeline for the underlying API: TypeScript's own [GA announcement](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/) (Jul 8 2026) states "TypeScript 7.0 does not ship with an API. We expect TypeScript 7.1 to ship with a new (and different) API." No committed date was found for 7.1 in any primary source; independent secondary estimates (e.g. digitalapplied.com) extrapolate "several months," consistent with TypeScript's historical ~3–4 month cadence putting 7.1 around Oct–Nov 2026 — but this is an inference, not an official commitment.

### (b) `@typescript-eslint` TS7 support

- Live npm registry check (2026-08-02): `@typescript-eslint/eslint-plugin`'s current peer dependency is `"typescript": ">=4.8.4 <6.1.0"` — TS7 is fully outside the declared range (and so, incidentally, is TS 6.1+).
- [typescript-eslint's own "Dependency Versions" doc](https://typescript-eslint.io/users/dependency-versions/): confirms the same `>=4.8.4 <6.1.0` range and states the project "only support[s] versions of TypeScript less than 2 years old," mirroring DefinitelyTyped's support window — i.e. this is policy, not an oversight.
- [Issue #12518, "TypeScript 7.0.2 Support"](https://github.com/typescript-eslint/typescript-eslint/issues/12518): a user reported `npm ci` failing outright on the peer-dependency check, and — when forced past it — ESLint crashing inside `typescript-estree` with `TypeError: Cannot read properties of undefined (reading 'Cjs')` (TS7 removed APIs typescript-estree references at module load, before any version guard can run). **Closed as "not planned."**
- [Issue #12521, "Show user-friendly message if TS 7 is detected?"](https://github.com/typescript-eslint/typescript-eslint/issues/12521): confirms the crash is structural — top-level code in typescript-estree touches TS APIs (e.g. `ts.Extension.Cjs`) that no longer exist in TS7, before any runtime version check executes. Labeled "accepting prs" (i.e., a real fix — even just a friendlier error — needs a contributed PR; none has landed).
- [Issue #10940, "Use TS 7 (tsgo / typescript-go) for type information"](https://github.com/typescript-eslint/typescript-eslint): tracks the deeper integration problem — ESLint's parser interface isn't async, but `tsgo` is expected to be consumed via async native-binding/WASM APIs, so typescript-eslint would need a `synckit`-style bridge with its own data-serialization complications. This is materially harder than Next.js's fix (which only needed to shell out to `tsc` instead of loading it as a module) and is not scoped to a release.
- **This blocker is upstream of the choice of framework.** It stems from the same missing Strada-compatible API that blocks Next.js, but requires typescript-eslint's own architectural rework, not just a "shell out to `tsc`" workaround — Next's own trick doesn't transfer to a lint parser, which needs live type information in-process.

### (c) Astro's TypeScript support and whether it's closer to TS7

- Astro's own tracking discussion, [`withastro/roadmap` discussion #1321, "TypeScript Native (`tsgo` / TypeScript 7) compatibility tracking"](https://github.com/withastro/roadmap/discussions/1321) (opened by `mwolson`, Mar 16 2026): states plainly that "the programmatic Language Service API is still in progress... The TypeScript team has indicated that the existing JS-based API surface ('Strada') will not be carried forward into TS 7, and a new API is being designed," and that `@astrojs/check`, `@astrojs/language-server`, and `@astrojs/ts-plugin` all depend on that Language Service API for `.astro` file type-checking and editor support. It has 44 👍 reactions but **zero maintainer replies** as of this research (Aug 2026) — no roadmap, no committed timeline.
- [Astro's official TypeScript guide](https://docs.astro.build/en/guides/typescript/) doesn't mention TS7/tsgo at all; type-checking is delegated to `astro check` (built on `@astrojs/check`), not performed inline during build — architecturally similar in spirit to Next's CLI-shim workaround, but Astro hasn't shipped an equivalent yet.
- Live npm registry check (2026-08-02): `@astrojs/check@0.9.10`'s peer dependency is `"typescript": "^5.0.0 || ^6.0.0"` — it has caught up to TS6 (an earlier GitHub issue, [#16112](https://github.com/withastro/astro/issues/16112), shows it was capped at `^5.0.0` as recently as March 2026 and was fixed to add `^6.0.0` support since) but **does not yet accept TS7 at all**, i.e. narrower than even typescript-eslint's range, let alone Next.js's now-working opt-in path.
- Net: Astro is not ahead of Next.js on TS7 — it is behind. Next.js has a working (experimental) opt-in path shipped in a stable release; Astro has an open tracking issue with no maintainer engagement and a type-checker that doesn't accept TS7 in any mode yet.

### Migration cost class: Next.js → Astro, in general terms

Not scoped to dtcg-editor's specific code, but characterized by kind of change:

- **Rendering model**: Astro's default "islands architecture" (mostly-static HTML, opt-in hydration per component via `client:*` directives) is a different mental model from Next.js's App Router (Server/Client Components, streaming, React Server Components by default). Existing React components can mostly be reused inside `.astro` files or as islands, but every page needs its hydration boundaries re-decided.
- **Routing & API routes**: Astro has its own file-based router and its own "endpoints" convention for API routes, not a drop-in match for Next's `route.ts` handlers, middleware, or `proxy.ts`/edge middleware conventions — these need re-authoring, not just moving files.
- **SSR/deployment**: Astro supports SSR via adapters (Node, Vercel, etc.) but the request/response lifecycle, caching primitives, and edge-runtime story differ from Next's; anything relying on Next-specific APIs (`next/navigation`, `next/link` typed routes, Next Image, ISR/cache components, instrumentation hooks) needs a rewrite or Astro-equivalent.
- **Ecosystem**: Any Next.js-specific libraries/plugins (next-auth-style integrations, Next-aware SEO/analytics packages) need Astro equivalents or custom replacements.
- **Class of effort**: this is a **major, whole-app rewrite**, not a moderate refactor — every page/route touches the new rendering and routing model, even though individual React components are largely portable. It is not a class of change worth taking on solely to get ahead of a TypeScript compiler-API gap that, per the findings above, Astro hasn't actually closed either.

## Net takeaway

**Waiting on (and re-testing) Next.js is clearly the better near-term path — and it may already be unblocked.** dtcg-editor is pinned to Next.js `16.2.12`, which already ships the `experimental.useTypeScriptCli` flag needed to run TypeScript 7 (backported 2026-07-23, two days before the blocking note was written). The backlog note's captured error is Next's own designed message for "TS7 installed but the flag isn't set" — not proof of incompatibility. The real, still-open blocker is `@typescript-eslint`, whose exclusion of TS7 is deliberate policy (not a quick peer-range bump) and requires either an async-parser bridge to `tsgo` (tracked, unresolved, issue #10940) or continuing to lint against a TS6 alias while the project itself runs TS7 for builds — a workaround pattern Next.js and Microsoft both explicitly document (`@typescript/typescript6` package, npm aliasing) and that would work identically whether the app is Next.js or Astro.

Astro is **not** meaningfully closer to unblocking TS7 — if anything it's a step behind: `@astrojs/check` only just gained TS6 support (was capped at TS5 until earlier this year) and doesn't accept TS7 in any mode, and Astro's own tracking discussion has sat with zero maintainer engagement since March 2026, versus Next.js's active, shipped, if experimental, fix. Because `@typescript-eslint`'s blocker is upstream of any framework choice, switching to Astro would not remove the one blocker that's actually still live — it would just add a **major, whole-app rewrite** (different rendering model, routing, API-route conventions, and ecosystem) on top of the same unresolved lint-tooling gap.

**Recommendation:** re-attempt the TS7 upgrade against current `16.2.12` with `experimental.useTypeScriptCli: true` enabled for the build/type-check step, while keeping `@typescript-eslint` on a TS6 alias (or simply staying on TS6 for lint until typescript-eslint ships real support). Do not pursue an Astro migration for this reason — it trades a well-understood, already-partially-solved blocker for a major rewrite that hits the identical upstream gap.
